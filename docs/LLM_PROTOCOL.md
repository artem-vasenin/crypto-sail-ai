# Локальная Qwen3-8B: контракт, границы, испытания

## 1. Реальный адрес сервера

- `http://127.0.0.1:8080/v1/chat/completions`
- Модель из текущего паспорта: `Qwen/Qwen3-8B-GGUF:Q4_K_M`
- llama.cpp уже установлен на Ubuntu. **Не** использовать `llm-agent:8090`, ChatGPT OAuth, Keychain, web-инструменты.
- В конфиге `llm_url` принудительно закреплён за localhost:8080. В тестах допустим другой локальный порт `httptest` для изоляции сети.

В POST отправляются `model`, `messages` (системная инструкция и валидированные данные), `temperature=0.1`, `max_tokens=1400`, `stream=false`, `response_format` вида `json_schema` с `strict=true`. Нет поля `tools`. Сервер должен завершить единственный ответ `finish_reason=stop`, иначе ошибка. `json.Valid` — только первая проверка; `internal/llm/schema.go` дополнительно проверяет структуру JSON (обязательные поля, запрет посторонних ключей, типы и enum), затем сверяются идентификаторы и прикладные ограничения.

## 2. Ранний triage

**Вход:** `snapshot_id` + массив `surface.Result` по максимуму `max_llm_batch` из свежих записей. Рядом с символом присутствуют цена/спред/оборот/доступность данных/причины. Модель **не** должна запрашивать Bybit самостоятельно.

**Выход (схема):**

```json
{
  "snapshot_id": "EXAMPLE_ID",
  "items": [
    {
      "symbol": "BTCUSDT",
      "side": "LONG",
      "decision": "REQUEST_DEEP_ANALYSIS",
      "reason_codes": ["need_htf_structure"],
      "explanation": "Признаки поверхностного снимка требуют проверки 4H"
    }
  ]
}
```

`items` должны соответствовать исходному батчу **один к одному** без посторонних и повторённых символов, с непустым объяснением и минимум одним непустым `reason_codes` на каждый инструмент (ограничение `minItems: 1` в schema + повторная проверка в Go). В точном смысле это запрос исследования, а не торговый сигнал. Тестируется в `internal/llm/client_test.go`.

## 3. Deep proposal

```json
{
  "snapshot_id": "EXAMPLE_ID",
  "symbol": "BTCUSDT",
  "side": "LONG",
  "decision": "WAIT",
  "reason_codes": ["late_entry"],
  "evidence": ["4H HH/HL"],
  "risks": ["Price near resistance"],
  "entry_low": 99,
  "entry_high": 100,
  "invalidate_at": 96,
  "explanation": "Направление потенциально приемлемо, точка входа пока нет"
}
```

Пример — синтетический; цены не реальные. `entry_low/entry_high/invalidate_at` остаются **предложением**, а не автоматически одобренным риск-планом. Для неизвестных уровней модель должна вернуть нули и WAIT/NEED_DATA. Неправильный snapshot/symbol, неверные enums, отсутствие reasons или частичный ответ приводят к ошибке. Дополнительные Go-gates могут понизить READY до WAIT/REJECT.

**Ограничение текущей проверки:** Go пока не подтверждает числовое соответствие всех evidence признакам снимка, а инструментальный PromptVersion не хранится per-call. Требуется последующее расширение.

## 4. Проверка «хватит ли Qwen»

`testdata/llm-benchmark.json` содержит **6 синтетических случаев**: перегретый LONG, конфликт HTF, отсутствие данных, SHORT у поддержки, неприемлемый спред/оборот и потенциальный LONG с неопределённостью. `sail benchmark` проверяет формат, latency, consumption и принадлежность решения к предварительным допустимым статусам. Это тест способности соблюдать контракт, **не** прибыли. При первом тесте оставить `--reasoning off`; только после базового протокола рассмотреть сравнение thinking-on/off с измерением VRAM и стоимости задержек.

План расширения: сотни сохранённых рыночных снимков, независимая разметка с исходами по времени, повторяемость ответов, способность обнаружить отсутствие данных и HTF конфликт, качество WAIT, сравнение с Go-only baseline. Запрещено оценивать успешность только по `confidence` или совпадению с заранее заданным классом.

## 5. Failure semantics

- `timeout`, HTTP non-200, ошибка JSON, не `stop`, неверный `snapshot_id`, неизвестный символ → **запрос не имеет валидного аналитического результата**.
- Ошибка LLM не преобразуется в `READY`, ответ не используется как приказ.
- Текущий CLI прерывает команду и не создаёт виртуальную позицию. Runtime future queue обязан хранить ошибку и переотправлять по ограниченным правилам.
- Часть `llm_calls` записывается даже для ошибок. Секреты и токены в промпт не передаются.

## 6. Инцидент и исправление triage (16.11.2026)

На настоящем Qwen3-8B получены пять `REQUEST_DEEP_ANALYSIS` с `side: NONE`, но с `reason_codes: []`: BTCUSDT, ETHUSDT, SOXLUSDT, SOLUSDT, XRPUSDT. Общая ошибка `invalid triage content` была верным отказом в принятии решений, но плохой диагностикой. С v0.1.1 массив причин обязан содержать >=1 элемент и отдельные элементы не могут быть пробельными; сообщение об ошибке указывает, например, `triage item=0 symbol=BTCUSDT field=reason_codes`.

Сырой контент отклонённого ответа передаётся в журнал `llm_calls` (если сервер вернул одну choice; при недоступности сервера контента нет). `reason_codes` не дополняются искусственно, и никакое отказавшее решение не записывается в `decisions`. Повторение входного статуса Surface не считается аналитическим основанием для REQUEST_DEEP_ANALYSIS, однако **честность/полнота обоснования пока проверяются исследованием**, а не строгой математической верификацией текста объяснения.
