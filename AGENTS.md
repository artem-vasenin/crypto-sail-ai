# AGENTS.md — обязательные правила для ИИ-агентов Crypto Sail AI

**Проект:** Crypto Sail AI. **Версия:** `v0.1.1-research`. **Язык документации и взаимодействия:** русский.  
**Целевой стек:** Go 1.23.2, Ubuntu 24.04 LTS, локальная Qwen3-8B Q4_K_M (`llama-server`), Bybit V5 public REST, SQLite.  
**Статус:** исследовательский прототип, **не торговая система**.

## 1. Порядок чтения

1. `README.md` — реальные пользовательские команды и ограничения.
2. `docs/AI_CONTEXT.md` — зачем проект создан, исторические ошибки, границы готовности.
3. `docs/ARCHITECTURE.md` — что **реально работает**, что запланировано.
4. `docs/FILE_INDEX.md` — предназначение каждого файла и пакета.
5. `docs/DECISIONS.md` — архитектурные решения.
6. `docs/TESTING_RU.md` — обязательная проверка изменений.
7. `docs/ROADMAP.md` — дальнейшие этапы, которые **не** следует выдавать за завершённые.
8. Исходный код и тесты: при конфликте документации с кодом проверять фактическое поведение тестом.

## 2. Абсолютные запреты

- **Никаких реальных биржевых ордеров**. Не добавлять приватные эндпоинты Bybit, подпись ключами, API secret, считывание `.env` для торговых ключей, `order/create`, leverage или операции с реальным счётом. Даже Testnet-исполнение — отдельный будущий milestone.
- Не считать `READY`, `confidence`, screener score или симпатичное объяснение Qwen вероятностью прибыльной сделки.
- Не считать, что `paper` выполняет реальную торговлю: текущий `paper` — офлайн replay с **предполагаемым уже исполненным входом**, а `EntryOrder` — отдельная консервативная модель возможных maker-fill.
- Не подключать `llm-agent:8090`, OAuth, ChatGPT, Keychain, OpenCode, SearXNG. **Прямой** локальный запрос к `127.0.0.1:8080/v1/chat/completions`.
- Не предоставлять Qwen инструменты или доступ к интернету. Go собирает публичные данные; Qwen их интерпретирует.
- Не открывать LLM API в сеть, не менять systemd-службу установленной Qwen без причины и обсуждения.
- Не переносить без аудита старые компоненты/пороги/код из проекта `Crypto-Sail-AI-v0.2.x`, в особенности live execution, трендовые оценки `0/33` и некорректный initial-R.
- Не возвращать отбор монет по абсолютной номинальной цене.
- Не снижать фильтры, чтобы искусственно увеличить число кандидатов.
- Не удалять/перезаписывать пользовательскую SQLite, журнал событий, снимки или исторические результаты. Сделать резервную копию перед миграцией.
- Не заявлять о проведённой live-проверке Bybit/Qwen, если её фактически не было; `httptest` — **не** проверка доступности биржи.

## 3. Система принятия решений

`Bybit public data → quality validation → Surface → Qwen triage → Go deep features → Qwen deep proposal → independent Go gates → REJECT/WAIT/READY → virtual research → statistics`.

Сейчас реализованы **командные отдельные шаги**, не непрерывный автономный конвейер. `triage` не запускает `deep` автоматически, `READY` не запускает `paper`, `watch-check` только сообщает триггер. Нельзя выдавать эти будущие связи за реализованные.

Измеряем отдельно **direction quality** и **entry quality**, включая `GOOD_DIRECTION_BAD_ENTRY`. Хорошее направление не компенсирует плохую точку входа. Отсутствующий pivot — `UNKNOWN`, а не bearish. LLM может запросить Deep или предложить Wait; любой неверный JSON, snapshot, symbol, недоступная LLM → **нет нового READY**.

## 4. Формальные инварианты

- Обработку structure/indicators делать только по закрытым UTC свечам. Проверять возраст, дубли, порядок, OHLC и историю; не использовать незакрытую свечу для исторического сигнала.
- Сохранять первичные значения, метку времени, `snapshot_id`, версию промпта/модели при расширении LLM; исходные числа важнее итоговых строк.
- `Go` вычисляет математику, Qwen не выдумывает факты. Полный вход Qwen доступен для воспроизводимости. Сейчас снимки сохраняются в SQLite, LLM метаданные/сырой ответ также сохраняются.
- `initial_risk_price` и `initial_risk_usdt` заморожены после виртуального fill. `R` всегда использует **исходный** риск.
- LONG Stop Loss может только повышаться, SHORT — только понижаться.
- Перенос в BE учитывает входную/выходную комиссию и заложенное проскальзывание, и не гарантирует фактический безубыток при гэпе.
- При пересечении SL и TP одной OHLC свечой симуляция консервативно выбирает SL первой. При гэпе исполнение стопа хуже уровня; не моделировать идеальное исполнение.
- PostOnly создание ≠ исполнение: только виртуальная имитация, отсутствие доказанных market trades не даёт считать лимитник filled.
- Watch entry zone ≠ вход: должен быть **новый Deep Snapshot** перед новым допуском.
- Grid не является directional LONG/SHORT и в текущем проекте не реализован.

## 5. Инструменты и среда

Go >= 1.23.2, `go.mod` сохраняет минимальную версию 1.23.2; пользователь проверил 1.27.x. Без автоматического скачивания нового toolchain:

```bash
GOTOOLCHAIN=local go version
make check              # test + race + vet + build
GOTOOLCHAIN=local CGO_ENABLED=1 go test ./...
GOTOOLCHAIN=local CGO_ENABLED=1 go test -race ./...
GOTOOLCHAIN=local CGO_ENABLED=1 go vet ./...
```

SQLite использует CGO и системную `libsqlite3`, поскольку из среды создания артефакта недоступна загрузка новых Go-модулей. На Ubuntu потребуются `build-essential libsqlite3-dev`. На продакшен без аудита зависимости/компилятора не переходить.

## 6. Как изменять код

1. Сначала определить один маленький функциональный инвариант, который меняется.
2. Найти соответствующий пакет и существующий тест из `docs/FILE_INDEX.md`.
3. Добавить failing unit/HTTP/SQLite test; отдельно обработать негативный сценарий.
4. Изменить минимальный объём Go-кода.
5. Выполнить `make check` и адресный тест, по возможности coverage.
6. При изменении контрактов обновить `README.md`, `docs/FILE_INDEX.md`, `docs/ARCHITECTURE.md`, `docs/TESTING_RU.md`, `docs/CHANGELOG.md`.
7. В итоговом сообщении: файлы, что изменилось, точные пройденные проверки, что не проверено, следующий маленький шаг.

Нельзя заменять тест сообщением «код должен работать». Не добавлять пустые пакеты и слои абстракции просто ради архитектуры.

## 7. Приоритеты следующих работ

1. Проверить на Ubuntu реальные Bybit public REST и Qwen baseline; фиксировать логи/ошибки.
2. Сверить `response_format=json_schema` со **фактическим** llama.cpp; проверить глубокие ответы, ошибки, schema violations, token truncation.
3. Превратить нынешние ручные команды в устойчивую очередь triage/deep с согласованием времени рыночных снимков и refresh TTL.
4. Добавить Market Collector с ограничением запросов и WebSocket; улучшить исполнение через публичные trade prints.
5. Довести WAIT state-machine, recheck deduplication, DB event log, replay engine и полноценный Paper Observer.
6. После накопления наблюдений — статистика, проверка гипотез, отдельно direction/entry.

## 8. История проекта

Новый репозиторий создан с нуля; прежний ZIP и материалы по Qwen служили **источником требований**. В старом скриннере `trend_quality` часто был `0/33` и отсекал большинство монет до ИИ; повторно использовать эту формулу без анализа запрещено. Старый агент для кодирования на 8090 технически независим от торговой аналитики. Краткая история и решения сохранены в `docs/AI_CONTEXT.md`.

## 9. Безопасное определение готовности

`go test ./...` и прохождение benchmark JSON подтверждают **только** тестируемые свойства. Для утверждения «Qwen улучшает торговлю» необходимы исходы на истории с исключённой утечкой будущего, наблюдение paper и статистическая значимость с учётом комиссий, проскальзывания и funding. **Не открывать реальные сделки без отдельного решения пользователя.**

## 10. Git и обновления

Перед изменениями проверять `git status`; все правки тестировать и коммитить малыми порциями. Никогда не добавлять `data/`, `bin/`, SQLite/WAL, архивы, конфиденциальные настройки и ключи. Руководство для первого Git-коммита: `docs/UPGRADE_AND_GIT_RU.md`.
